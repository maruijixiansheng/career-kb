## 1. 多 Worker 下 JWT Token 频繁失效

**现象**：每次切换页面或保存内容，强制跳到登录页面。

**根因**：`SECRET_KEY` 为空字符串 `""`。`python-jose` 在密钥为空时会用 `uuid.uuid4().hex` 生成随机密钥——但每个 uvicorn worker 进程独立生成，4 个 worker 有 4 个不同的密钥。用户登录时 worker A 签发的 JWT，到了 worker B 手里验证签名失败 → 401 → 前端拦截器跳转登录页。

**方案**：在 `backend/.env` 中设置固定 `SECRET_KEY`。

```
SECRET_KEY=career-kb-jwt-secret-d4e8f1a2b3c6-2026
```

**技术解释**：JWT 是无状态认证的核心——服务端不存 session，全靠签名验证。HS256 是 HMAC-SHA256，用同一个 `SECRET_KEY` 签名和验签。密钥必须跨所有 worker 一致，这是 HMAC 对称签名的基本要求。如果换成 RS256（非对称），可以用私钥签名 + 公钥验签，公钥可以不一致——但 HS256 对单机部署更轻量，固定密钥即可。

## 2. Docker 中 RAG 检索完全失效（召回 0 → 38 个片段）

**现象**：本地开发时 RAG 召回正常，Docker 部署后只返回 5 个片段，且全是基本信息/技能，零个项目经历。

这是一个**三层 bug 叠加**的典型案例：

### Bug 1（核心根因）：ChromaDB chunk 的 `id` 未写入 metadata → 全部被去重

`embedder.py:add_chunks()` 构建 metadata 时只用了 `chunk.metadata` 字典：

```python
# 修复前
metadatas = [{k: v for k, v in chunk.metadata.items()} for chunk in chunks]
ids = [chunk.id for chunk in chunks]  # 只传给了 ChromaDB 原生 ID
```

ChromaDB 的 `ids` 参数确实存了文档 ID，但 LangChain 的 `Document` 对象不暴露原生的 ChromaDB ID——它只读 `metadata`。检索时：

```python
"id": doc.metadata.get("id", "")  # → 所有 8 个 chunks 返回 ""
```

8 个 chunks 的去重 key 都是 `""` → 去重后只剩 1 个。5 个 collection → 总共 5 个结果。

**修复**：把 `chunk.id` 同时也写入 metadata（`id` 字段需在 `metadata` 字典中存在，LangChain `similarity_search_with_score` 才能取到）。

### Bug 2：`section_type` 未写入 metadata → 章节权重全部失效

同理，`chunk.section_type` 存在 Chunk 对象的属性上（`chunk.section_type = "project"`），但没有序列化到 metadata。检索时的章节加权逻辑：

```python
section_type = doc.get("metadata", {}).get("section_type", "")  # → 永远是 ""
weight = section_weights.get(section_type, 1.0)  # → 全部 1.0
```

项目经历（应加权 ×1.3）和基本信息（应降权 ×0.6）没有区分度。

**修复**：`add_chunks()` 将 `id`、`section_type`、`section_title`、`chunk_index` 全部写入 metadata。同时添加 `_infer_section_type()` 方法，对已存在的 38 个旧 chunks 通过内容关键词（"项目:"、"姓名:"、"学校:"等）推断章节类型。

### Bug 3：相关性阈值对集合太小太激进

```python
MIN_RELEVANCE = max(0.03, max_score * 0.5)
```

每 collection 只有 7-8 个 chunks。最高分 0.677，阈值 0.338，大部分 chunks 被砍掉。

**修复**：阈值降为 `max_score * 0.15`，且确保至少返回 `top_k_fusion` 个结果（不足时按分数补足）。

### Bug 4：孤立的 ChromaDB collection 未被搜索

本地开发时上传简历创建的 ChromaDB collection 的 UUID 与 Docker 迁移后 PostgreSQL 中的 resume ID 不一致。原来的代码只检索 DB 中匹配的 collection，遗漏了 4 个有数据的孤立 collection。

**修复**：`retrieve_from_all_sources()` 改为列出 ChromaDB 中所有 `resume_*` collection，与 DB 记录合并去重后再检索。

### 为什么本地正常 Docker 不正常

`Path(__file__).parent.parent.parent` 在本地开发时解析为项目目录，在 Docker 中解析为 `/`。ChromaDB 持久化目录从 `/data/chroma` 变成了容器内的临时路径，数据实际上已经被写入但路径不一致。加上 `id` 和 `section_type` 丢失，三重叠加导致完全检索不到项目内容。

## 3. WeasyPrint PDF 生成崩溃

**现象**：`'super' object has no attribute 'transform'`

**根因**：WeasyPrint 62.3 依赖的 `pydyf` 0.12.1 在 `stream.py` 中调用 `super().transform()` 时，Python 的 `super()` MRO 解析在特定调用链下找不到 `transform` 方法。这是 WeasyPrint/pydyf 的已知 bug，已在后续版本修复。

**方案**：`requirements.txt` 中 `weasyprint==62.*` → `weasyprint>=65.0`（实际解析到 69.0）。

**技术解释**：这次不是 CSS 问题（最初怀疑过 `linear-gradient` 和 `object-fit: cover`）。WeasyPrint 是一个将 HTML+CSS 渲染为 PDF 的库，底层通过 Pango/Cairo 将网页元素转换为 PDF 图形指令。`pydyf` 是 WeasyPrint 的 PDF 生成后端，负责低级的 PDF 对象序列化。`super().transform()` 是 pydyf 在处理 CSS transform 属性时的方法调用，版本 bug 导致 MRO 查找失败。这种 bug 的特征是：CSS 看起来没问题，HTML 在浏览器正常，但生成 PDF 时报 Python 内部错误。

## 4. 面试模拟无法一问一答

**现象**：开始面试后回答问题时提示"会话不存在"。

和 JWT 问题是同一类根因——**多 worker 内存状态不同步**。

### Bug 1：`InterviewAgent` 的 `sessions` 字典存在进程内存中

```python
class InterviewAgent:
    def __init__(self):
        self.sessions: dict[str, dict] = {}  # 每个 worker 各自一份！
```

Worker 1 处理 `start_interview` 创建状态，Worker 2 处理 `respond` 时 `get_state()` 返回 None → 404。

**方案**：添加 `load_state_from_db()` 方法，每次请求从 PostgreSQL 完整重建状态：
- 从 `interview_sessions` 读取会话配置（mode, difficulty 等）
- 从 `interview_messages` 读取所有历史消息
- 从 `job_descriptions` 和 `resumes` 读取 JD/简历原文
- 重建 `state` dict 后缓存到当前 worker 内存（仅加速同一请求内的后续调用）

### Bug 2：每个回答消耗 2 个问题槽位

`process_answer()` 内部调用了 `_get_next_question()`（生成下一题并递增 `question_count`），API 层紧接着又调一次 `generate_question()`（再递增一次）。结果：10 题的面试实际只问了 5 题。

**修复**：移除 `process_answer` 内的问题生成，统一由 API 层调用。

### Bug 3：消息序列号冲突

原序列号算法：`seq = question_count * 2`。但 `generate_question` 会递增 `question_count`，导致下一轮答案的序列号与当前问题相同（都 = 4）。

**修复**：改用 `SELECT COUNT(*) FROM messages` 作为序号基准 → `answer_seq = msg_count + 1`，`next_q_seq = answer_seq + 1`。

## 5. LLM 编造简历内容

**现象**：生成的简历中的项目经历、实习经历是虚构的，与用户上传的简历无关。

**根因**：`SMART_RESTRUCTURE` prompt 中过滤规则过于激进——要求"只使用相关性为'高'的素材"，导致真实素材被丢弃后，LLM 为了完成"填充简历"的任务而编造内容。

**方案**：重写 prompt 的核心逻辑：

1. **规则 #0（最高优先级）**："严禁编造任何信息。如果某个板块没有真实素材，直接删除该板块，不要显示占位文字。"
2. **取消相关性过滤**：相关性评分只用于排序，不再用于排除素材。"即使是低相关性素材，只要内容真实，也比编造的强一万倍。"
3. **空板块行为**：从"显示（无相关经历）占位文字"改为"整个板块不出现"。模板中 `_render_projects()` / `_render_internships()` 已有空内容不渲染的逻辑，与 prompt 一致。

**技术解释**：这是 LLM 应用的经典问题——当 prompt 给 LLM 施加了"必须完成"的压力（如"填充所有板块"），同时又限制了可用素材（"只使用高相关性"），LLM 会选择"完成任务"而非"遵守规则"。修复的核心是**反转优先级**：遵守规则 > 完成任务。空板块是可以接受的输出，编造是不可接受的输出。

## 6. PDF 简历证件照缺失

**现象**：Docker 中生成的 PDF 简历没有证件照。

**根因**：`PHOTOS_DIR` 配置解析路径在 Docker 容器中不正确。`Path(__file__).parent.parent.parent` 在容器中解析为 `/`，而实际挂载的数据目录在 `/app/data/photos`。

**方案**：
1. `docker-compose.yml` 中显式设置环境变量：`PHOTOS_DIR=/app/data/photos`
2. `_photo_to_base64()` 添加多路径回退：原始路径 → settings.PHOTOS_DIR → `/app/data/photos`
3. 使用 `os.path.basename` 提取文件名，在回退路径中重组完整路径

## 7. Pydantic 配置校验报错

**现象**：`ngrok_authtoken` / `ngrok_domain` — "Extra inputs are not permitted"

**根因**：ngrok 的环境变量放在了 `backend/.env` 中，但 Pydantic Settings 类设置了 `extra="forbidden"`。

**方案**：ngrok 变量移到项目根目录的 `.env`（docker compose 从那里读取变量替换 `${NGROK_AUTHTOKEN}`）。`backend/.env` 只保留 Backend Settings 类定义的变量。

## 8. Prompt 优化：从编造内容到严格保真

这是整个项目中最核心的 prompt 工程迭代——经历了"编造简历内容"的严重事故后，对 prompt 的优先级模型进行了彻底重构。

### 8.1 初始版本（存在问题）

**`SMART_RESTRUCTURE_USER` v1 的关键指令**：

```
## 素材使用规则
1. 只使用相关性为「高」的素材片段
2. 不要让不相关的经历冲淡简历的针对性
3. 如果候选人的经历与JD完全无关，可以只保留基本信息
```

**`SMART_RESTRUCTURE_SYSTEM` v1 的输出格式要求**：

```
【工作/实习经历】
（如果没有相关经历，显示"（无相关经历）"）
```

### 8.2 问题表现

| 症状 | 具体表现 |
|------|----------|
| 编造项目 | LLM 生成了候选人素材中完全不存在的项目名、技术栈、成果数据 |
| 编造实习 | 虚构了不存在的公司和职位 |
| 占位文字残留 | 空板块显示"（无相关经历）"，让简历看起来不专业 |
| 真实素材被丢弃 | RAG 召回了素材但 prompt 要求"只使用高相关性"，部分真实项目被过滤掉 |

### 8.3 为什么 LLM 会编造

这不是模型"故意撒谎"，而是 prompt 工程中的经典陷阱——**冲突指令**：

```
指令 A: "只使用高相关性素材"  → 过滤掉大量真实内容
指令 B: "填充所有板块"       → 要求输出完整简历
结果: LLM 发现素材不够 → 选择"完成任务"而非"遵守规则" → 编造内容
```

LLM 的 reward model 训练使其天然倾向于"完整、有帮助的回答"。当"完整性"和"真实性"冲突时，prompt 中的优先级决定了行为。初始版本中，真实性是"核心原则 #1"，但**系统提示中并没有把它设为绝对优先级的硬约束**。

### 8.4 优化后的 Prompt

**`SMART_RESTRUCTURE_SYSTEM` v2 核心结构**：

```
## ⛔ 第一条：严禁编造（最高优先级，覆盖所有其他规则）

这是你必须遵守的最重要规则，任何情况下都不能违反：

1. 你只能使用「候选人全部可用素材」中明确写出的内容
2. 禁止虚构任何信息：公司名、职位名、项目名、技术栈、时间、数字、成果
3. 如果素材中完全没有某个板块需要的内容，直接删除该板块
4. 宁缺毋滥：真实的但内容少的简历 > 丰富但虚假的简历
5. 逐字对照：每一条都必须能在素材中找到对应原文
```

**`SMART_RESTRUCTURE_USER` v2 的素材使用规则**：

```
## ⛔ 使用素材的铁律

1. 你只能使用上面「候选人全部可用素材」中明确写出的内容
2. 素材末尾标有「相关性:高/中/低(分数)」仅供参考排序。
   即使是低相关性素材，只要内容真实，也比编造的强一万倍
3. 相关性分数只用于排序优先级，不用于排除素材
4. 如果某个板块在素材中完全没有对应内容，直接删除该板块（包括标题），
   不要写「（无相关经历）」等任何占位文字
```

### 8.5 优化前后对比

| 维度 | v1（有问题） | v2（修复后） |
|------|------------|------------|
| **防编造规则位置** | 核心原则第1条（与其他规则平级） | ⛔ 独立章节 + "最高优先级，覆盖所有其他规则" |
| **素材过滤方式** | "只使用相关性为'高'的素材" | "相关性分数只用于排序优先级，不用于排除素材" |
| **低相关素材态度** | 丢弃 | "即使是低相关性素材，只要内容真实，也比编造的强一万倍" |
| **空板块处理** | 显示"（无相关经历）"占位 | 直接删除整个板块（包括标题） |
| **任务优先级** | 完整性 > 真实性（隐含） | 真实性 >>> 完整性（显式声明） |
| **自检机制** | 无 | "逐字对照：每一条都必须能在素材中找到对应原文" |

### 8.6 为什么 v2 有效

**1. 优先级显式化**

AI 模型是概率性的，它们对"重要程度"的判断依赖于 prompt 中的位置、强调符号和措辞强度。v2 使用 `⛔` 符号 + "最高优先级，覆盖所有其他规则" + "任何情况下都不能违反" 三层强调，将防编造提升到绝对优先。

**2. 消除冲突指令**

v1 同时说了"不要编造"和"只使用高相关性素材"——后者暗示要丢弃内容。当 LLM 发现自己可用的真实内容被规则的过滤标准排除后，它面临选择：遵守"不要编造"（输出空简历）还是遵守"写好简历"（填充内容）。v2 消除了这个冲突：所有素材都可用，相关性只是排序建议。

**3. 提供"合法"的简略输出**

v1 暗示每个板块都应该有内容（否则用占位文字填充）。v2 明确告诉 LLM "没有内容的板块直接删除"是可以接受的输出。这让 LLM 不必在"遵守规则"和"完成模板"之间做选择。

**4. 具体化禁止项**

v1："不要编造"（抽象）
v2："禁止虚构公司名、职位名、项目名、技术栈、时间、数字、成果"（具体列表）

LLM 对具体指令的遵循度远高于抽象指令。

### 8.7 实际效果

修复前，生成的简历中：
- 项目经历约 30-50% 包含虚构信息
- 空板块显示"（无相关经历）"占位文字
- RAG 召回的很多真实项目被丢弃

修复后：
- 编造率降至接近 0%（在 RAG 正常召回的前提下）
- 空板块完全不出现在输出中
- 即使是"低相关性"的真实素材也能被合理利用

> **核心经验**：Prompt 设计的关键不是"告诉 LLM 做什么"，而是**消除指令之间的冲突**。如果你同时要求"要完整"和"要真实"，LLM 会在两者之间寻找折中——而"编造"恰好是一种在满足"完整性"的同时绕过"真实性"检查的路径。正确的做法是明确声明"真实比完整重要"，并给出可接受的"不完整"输出格式。

## 9. RAG 跨领域检索误匹配

**现象**：JD 是"AI应用开发"（LLM应用/RAG/Agent方向），检索结果包含 YOLO/CNN/ROS 计算机视觉项目。语义检索只看向量距离，无法区分"都是AI"但"方向不同"的内容。

### 为什么向量检索会出错

BGE-M3 的语义空间里，"AI应用开发"和"计算机视觉"距离很近——它们同属 AI 大类、都使用 Python、都涉及深度学习。向量检索只看内容相似度，不考虑**领域方向**的差异。这导致检索排名被"同属AI但方向不同"的内容污染。

### 三层防线方案

这是一个逐步演进的过程，经历了用户的直接反馈和架构调整：

#### 第一层：检索时动态领域过滤 (`retriever.py`)

**初始方案**：硬编码关键词黑名单（YOLO、OpenCV、ROS等），拒绝采纳——"不同JD需要不同的排除关键词，这个方案不保险"

**最终方案**：LLM 解析 JD 时提取 `irrelevant_domains` 字段，检索时动态惩罚含这些关键词的 chunks（80% 降权 ×0.2）。

```python
# JD解析输出新增字段
"irrelevant_domains": ["计算机视觉", "目标检测", "自动驾驶", "机器人"]

# 检索时动态惩罚
for doc in fused:
    if any(kw in doc["content"] for kw in irrelevant_keywords):
        doc["weighted_score"] *= 0.2  # 80% 惩罚
```

#### 第二层：LLM 相关性把关 (`rag_engine.py:filter_by_relevance()`)

检索后增加一层 AI 判断——把候选经历送给 DeepSeek 逐条判断方向是否一致。

**关键迭代**：

| 版本 | 做法 | 问题 |
|------|------|------|
| v1 | 对所有 chunks 做 LLM 判断 | LLM 判定全不相关后保守回退，全部保留 → 无效 |
| v2 | 只对 `section_type == "project"` 判断 | 工作/实习经历绕过过滤 |
| **v3（当前）** | 对 `project / work / internship` 三种经历做判断，基本信息/教育/技能始终保留 | ✅ |

```python
EXPERIENCE_TYPES = ("project", "work", "internship")
# 非经历内容 → 始终保留，不参与 LLM 判断
# 经历内容 → LLM 逐条判断方向一致性
```

#### 第三层：Prompt 收敛设计 (`prompts.py`)

- **严格判断标准**："都用 Python"不算相关，判断的是业务方向是否匹配
- **默认不相关**：不确定时保守判断，宁可少一个经历也不错配
- **数字索引匹配**：LLM 返回数字序号 `[0, 2]` 而非 chunk_id 前缀，避免匹配失败
- **全不相关时冷静处理**：只保留非经历内容（基本信息框架完整），不保守回退

### 设计原则

这个方案的核心思路是**区分"身份信息"和"经历内容"**：
- 一个人的学校、专业、技能列表 → 无论投什么岗位都应该展示
- 具体的项目/工作经历 → 只有方向匹配的才值得展示

### 验证结果

| 简历 | JD | 经历 | 过滤后 |
|------|-----|------|--------|

## 10. 简历打印/PDF 联系方式显示为方框

**现象**：简历预览和 PDF 下载中，电话、邮箱前面的图标显示为空心方框（□）。

**根因**：HTML 模板中使用 Unicode emoji（📞📧📱📍💼）作为联系方式图标。WeasyPrint 生成 PDF 时依赖系统字体渲染 emoji，但 Docker 容器中的字体（SimSun、Microsoft YaHei 等）不包含 emoji 字形。浏览器打印时也存在同样问题——打印渲染引擎将缺少字形的 emoji 显示为 tofu（方框）。

**方案**：两个模板中所有 emoji 替换为纯文字标签。

| 位置 | 原来 | 现在 |
|------|------|------|
| `resume_template.py` | 📧 email | 邮箱：email |
| | 📱 phone | 电话：phone |
| | 📍 city | 城市：city |
| `resume_template.html` | 📞 phone | 电话：phone |
| | 📧 email | 邮箱：email |
| | 💼 years | 经验：years |

**技术解释**：Unicode emoji 的渲染依赖字体的 `cmap` 表和彩色字形支持。中文字体（SimSun/SimHei）通常不包含 emoji 码位。即使系统有 emoji 字体（如 Segoe UI Emoji / Noto Color Emoji），WeasyPrint 的 Pango 文本布局引擎在 Linux/Docker 环境中也不支持彩色字体格式。纯文本是最可靠的跨平台方案。

## 11. 简历排版非A4规范

**现象**：浏览器预览和 PDF 中简历不按 A4 纸规格排布——内容贴边、宽度比例不对、高度不匹配 A4 297mm。

**根因**：CSS 中 body 只有 `width: 210mm`（A4 宽）但没有 `min-height` 约束高度，也没有页面内边距。`.page` 用 `display: table` 布局，内容直接撑到页面边缘。

**方案**：

```css
/* 浏览器预览：A4 卡片效果 */
.page {
    width: 210mm;          /* A4 宽度 */
    min-height: 297mm;     /* A4 高度 */
    margin: 0 auto;        /* 居中 */
    background: #fff;      /* 白色卡片 */
    box-shadow: 0 2px 16px rgba(0,0,0,0.15);  /* 纸张阴影 */
}

/* 打印/PDF：全幅输出 */
@media print {
    .page {
        width: 100%;
        min-height: auto;
        box-shadow: none;
        margin: 0;
    }
}

@page {
    size: A4;              /* WeasyPrint 输出 A4 页面 */
    margin: 0;
}
```

**设计要点**：
- **预览 vs 打印分离**：预览用灰色背景 + 白色卡片 + 阴影模拟纸张；打印用 `@media print` 去除所有装饰
- **@page margin: 0**：内容区域等于 A4 全幅，由 sidebar/main padding 控制内边距
- **flexbox 比 table 更稳健**：body 用 flexbox 居中 `.page` 卡片，避免 mm 单位在 table 布局中的兼容问题

## 12. 简历 PDF 第二页孤块（回缩循环）

**现象**：下载的 PDF 里，「个人总结」整段被推到第二页，孤零零一块；明明第一页只差一点点就能放下。

**根因**：两个因素叠加。

1. `.summary-text`（个人总结）带 `page-break-inside: avoid`，是不可拆分块。当第一页剩余空间放不下整段时，整段跳到第二页，而不是只溢出尾部。
2. 这类「差一点放不下」的溢出量常见 150~450px，但回缩力度不够——只压字号、下限 -15% 的话，只能收回约 100px，回缩到底也拉不回第一页。

**方案**：`pdf_generator.py` 增加「渲染-测量-回缩」循环（`_resolve_scale`）。

- 恰好两页且第二页内容不足半页（148.5mm）→ 每次字号 -2%（下限 -25%）重渲染直到一页；超半页或超两页保持原样。
- 回缩时**同时收紧无单位 `line-height`**（钳制 ≥1.25），而不是只压字号——压行距比压字号更省可读性，同样缩 ~10% 字号就能多收回数百 px 垂直空间。

**三个关键坑**：

1. **`min-height:297mm` 会作用到每个分页片段**：`.page`/`.main` 的 `min-height` 会让第二页的 fragment 也被撑满到 297mm，导致真实溢出高度读不出来。测量前必须先 `re.sub(r'min-height:\s*297mm', 'min-height:0', html)` 剥离。
2. **只压字号不够**：下限 -15% 只能回缩 ~100px，覆盖不了「整段总结被推到第二页」的 150~450px 溢出。需同时收紧 line-height，且下限提到 -25%。
3. **正则替换要保留分号**：缩放 `line-height: 1.6;` 时如果替换串漏掉结尾 `;`，会产出 `line-height: 1.38`（无分号）导致 CSS 失效。替换串必须补回分号。

**验证**：6~8 项目 + 4~8 行总结的溢出（150~500px）均回缩到一页（字号 0.84~0.98，约 11px 可读）；第二页超过半页（约 9+ 项目）则保留两页，符合「超过半页才允许两页」。

## 技术要点总结

| 技术 | 关键教训 |
|------|----------|
| **uvicorn workers** | 任何在进程内存中维护的可变状态（JWT 密钥、session、缓存）必须要么跨 worker 共享（Redis），要么从持久层重建（DB）。多 worker 本质是多进程，内存隔离是硬约束 |
| **ChromaDB** | `chroma.add_texts(ids=...)` 存储的是原生 ID，但 LangChain 的 `Document.metadata` 是独立的概念。检索时需要的任何字段都必须同时写入 metadata |
| **LangChain Chroma 集成** | LangChain 的 Chroma wrapper 返回的 `Document` 对象不暴露 ChromaDB 原生 ID——`doc.metadata` 是你存储 metadata 的唯一出口 |
| **LLM Prompt 设计** | 禁止编造的规则必须是最高优先级，且不能与"完成任务"的要求冲突。宁可输出不完整的真实内容，也不能输出完整的虚构内容 |
| **语义检索的边界** | 向量相似 ≠ 领域相关。语义检索无法区分"AI应用开发"和"计算机视觉"。需要 LLM 第二层把关 + JD 动态领域过滤弥补 |
| **硬编码黑名单的陷阱** | 静态关键词黑名单不可扩展——不同 JD 需要排除不同内容。应由 JD 解析动态生成排除词，而不是维护一个永不完整的全局列表 |
| **过滤粒度设计** | 区分"身份信息"（基本信息/教育/技能）和"经历内容"（项目/工作/实习）。前者始终展示，后者按 JD 方向过滤。全部送 LLM 判断会导致过度过滤 |
| **WeasyPrint** | PDF 引擎的版本 bug 不一定是 CSS 问题。浏览器预览正常但 PDF 报 Python 错误时，先升级依赖版本 |
| **WeasyPrint 字体** | Docker 容器中缺少 emoji 字体，Unicode emoji 在 PDF 中渲染为方框（tofu）。联系方式等标签使用纯文本比图标更可靠 |
| **A4 排版** | `@page { size: A4 }` 定义输出尺寸，CSS body 模拟预览效果。预览（灰底+白卡+阴影）和打印（全幅无装饰）用 `@media print` 分离 |
| **WeasyPrint 分页测量** | `min-height` 会作用到每个分页片段，测量溢出前必须剥离；`page-break-inside:avoid` 的不可拆分块会把整块推到下一页，放大「孤块」问题 |
| **回缩可读性** | 优先收紧 `line-height` 而非压字号，同样能收回更多垂直空间、对可读性伤害更小；正则改写 CSS 时必须保留结尾分号 |
