## 一、基础设施层

### 1.1 Docker

**Docker** 是一个容器化平台，将应用及其所有依赖打包到一个隔离的"容器"中运行，确保在任何机器上行为一致。

| 在项目中的作用 |
|---------------|
| 将整个应用拆分为 4 个独立容器（PostgreSQL、Backend、Nginx、ngrok），每个容器各司其职 |
| 通过 `docker-compose.yml` 编排启动顺序：数据库 → 后端 → Nginx → 内网穿透 |
| `docker compose -p career-kb up -d` 一条命令启动全部服务 |
| `docker compose -p career-kb --profile tunnel up -d` 额外启动 ngrok 公网隧道 |

**技术选型理由**：避免"在我机器上能跑"的问题，生产环境和开发环境完全一致。

---

### 1.2 Nginx

**Nginx** 是一个高性能的 HTTP 服务器和反向代理。它的特点是轻量、并发能力强、配置灵活。

| 在项目中的作用 |
|---------------|
| **反向代理**：将 `/api/*` 请求转发到后端 FastAPI（端口 8000），实现前后端分离 |
| **静态文件服务**：直接托管前端构建产物（`dist/` 目录），用户访问 `/` 即看到 React 页面 |
| **SPA 路由支持**：`try_files $uri /index.html`，确保刷新页面时不会 404 |
| **SSE 长连接**：代理超时设为 300 秒，保证简历流式重组不被中断 |

**技术选型理由**：Nginx 是业界最成熟的反向代理方案之一，Alpine 镜像仅 ~10MB，启动快、占用低。比直接暴露 Uvicorn 更安全、性能更好。

---

### 1.3 ngrok

**ngrok** 是一个内网穿透工具，能将你本地的 HTTP 服务映射到一个公网 HTTPS 地址，让外网用户可以直接访问你电脑上的服务。

| 在项目中的作用 |
|---------------|
| 将本地 `nginx:80` 映射到公网域名 `https://unselect-thumping-encourage.ngrok-free.dev` |
| 无需购买云服务器、配置域名备案、设置路由器端口转发，即可让面试官/朋友远程访问 |
| 通过 `--profile tunnel` 可选启动，不影响正常本地开发 |

**技术选型理由**：个人项目不需要 7×24 在线，ngrok 免费版即可满足临时分享需求。

### 1.4 数据库

#### SQLite

**SQLite** 是一个嵌入式关系数据库，整个数据库就是一个 `.db` 文件，不需要安装任何数据库服务。

| 在项目中的作用 |
|---------------|
| 本地开发时使用，零配置，开箱即用 |
| 数据存储在 `data/career.db`，备份只需复制这一个文件 |

#### PostgreSQL 16

**PostgreSQL** 是企业级开源关系数据库，支持高并发、复杂查询、JSON 字段、全文搜索等高级功能。

| 在项目中的作用 |
|---------------|
| Docker 生产环境默认使用 PostgreSQL |
| 通过环境变量 `DATABASE_TYPE=postgres` 一键切换 |
| 4 个 Uvicorn worker 共享连接池，支持多用户并发访问 |

#### SQLAlchemy 2.0（异步）

**SQLAlchemy** 是 Python 最流行的 ORM（对象关系映射）框架，让你用 Python 类操作数据库表，而不需要手写 SQL。

| 在项目中的作用 |
|---------------|
| 18 个 ORM 模型（User、Resume、Application、Interview 等）映射到数据库表 |
| 异步引擎（`AsyncSession` + `asyncpg`/`aiosqlite`）不阻塞事件循环 |
| 自动建表 + 自动追加缺失列，安装即用 |

#### Alembic

**Alembic** 是 SQLAlchemy 官方的数据库迁移工具，像 Git 一样版本化管理数据库结构变更。

| 在项目中的作用 |
|---------------|
| 记录每次表结构变更（如添加字段、创建索引）为迁移脚本 |
| 支持升级和回滚，多人协作不冲突 |

**技术选型理由**：SQLite 本地零配置 + PostgreSQL 生产高并发，双数据库模式兼顾开发体验和生产可靠性。

## 二、后端核心

### 2.1 FastAPI

**FastAPI** 是目前最快的 Python Web 框架之一，基于 Starlette 和 Pydantic，原生支持异步、自动生成 API 文档。

| 在项目中的作用 |
|---------------|
| 提供 9 个路由模块、30+ API 端点 |
| 自动生成 Swagger 文档（`/docs`）和 OpenAPI Schema（`/openapi.json`） |
| 类型安全：请求参数、响应数据全部由 Pydantic 校验 |
| 依赖注入系统：`get_current_user` 自动解析 JWT 并注入当前用户 |

#### Uvicorn

**Uvicorn** 是一个基于 uvloop 的 ASGI 服务器，专为异步 Python 设计。

| 在项目中的作用 |
|---------------|
| 生产环境 4 个 worker 并行处理 HTTP 请求 |
| 支持 SSE 长连接（简历流式重组） |

### 2.2 Pydantic

**Pydantic** 是一个数据校验库，通过 Python 类型注解定义数据模型，自动校验和转换。

| 在项目中的作用 |
|---------------|
| `schemas.py` (~320 行) 定义所有 API 的请求体和响应体结构 |
| `config.py` 用 `BaseSettings` 从 `.env` 文件加载配置，自动校验必填字段 |

### 2.3 认证与安全

#### JWT（JSON Web Token）

**JWT** 是一种无状态认证令牌，用户登录后服务器签发一个加密的 token，后续请求携带此 token 即可识别身份，服务器不需要存 session。

| 在项目中的作用 |
|---------------|
| 用户登录后签发 JWT（HS256 签名，24 小时过期） |
| 前端存入 localStorage，每次请求通过 Axios 拦截器自动附加到 Header |
| `get_current_user` 依赖注入自动解析 token 并加载用户信息 |

#### bcrypt

**bcrypt** 是一个密码哈希算法，特点是计算慢（故意慢），即使数据库泄露，攻击者也难以暴力破解密码。

| 在项目中的作用 |
|---------------|
| 注册时对密码进行 bcrypt 哈希后存入数据库 |
| 登录/修改密码时验证用户输入的密码 |

#### 全局限流器

| 在项目中的作用 |
|---------------|
| LLM 相关端点每分钟限 5 次（防止 API 费用失控） |
| 全局端点每分钟限 100 次（防止恶意刷接口） |

## 三、AI / 大模型层

### 3.1 DeepSeek Chat

**DeepSeek** 是深度求索公司开发的大语言模型，性能对标 GPT-4，支持 127K 上下文窗口，中文能力出色，API 价格远低于 OpenAI。

| 在项目中的作用 |
|---------------|
| **简历重组**：根据 JD 要求，从原始简历中选取最匹配的经历重新组织语言 |
| **JD 解析**：从职位描述中提取技术要求、加分项、软技能等结构化信息 |
| **面试模拟**：扮演面试官进行多轮技术/行为面试，并给出 5 维评分报告 |
| **技能 Gap 分析**：对比简历技能和 JD 要求，计算差距分数并生成学习路径 |
| **无回应分析**：分析投递后无回应的可能原因，生成跟进策略 |
| **事实核查**：对比重组后的简历和原始简历，确保没有编造内容 |

### 3.2 LangChain

**LangChain** 是一个 LLM 应用开发框架，封装了大模型调用、Prompt 管理、Chain 编排等常见模式。

| 在项目中的作用 |
|---------------|
| `ChatOpenAI` 兼容接口封装 DeepSeek API 调用 |
| `ChatPromptTemplate` 管理所有 Prompt 模板（`core/prompts.py` ~830 行） |
| 提供 token 计数、成本估算、审计日志等功能 |

### 3.3 LangGraph

**LangGraph** 是 LangChain 团队开发的状态图编排引擎，用于构建复杂的多步 AI Agent 工作流。

| 在项目中的作用 |
|---------------|
| **RAG Pipeline（7 节点）**：解析 JD → 生成查询 → 混合检索 → 格式化 → 重组 → 分析提取 → 事实核查 |
| **无回应分析 Agent**：3 路并行分析（简历匹配度、市场竞争、投递策略）→ 综合建议 |
| **技能 Gap Agent**：提取 JD 技能权重 → 对比简历技能 → 计算加权分数 → 生成学习路径 |
| **面试 Agent**：从数据库重建对话状态（多 worker 安全），管理 10 轮对话上限 |

**技术选型理由**：简历重组不是一次 LLM 调用能完成的，需要检索→重组→核查的多步流水线，LangGraph 的状态图比手写 if-else 更清晰、可观测。

### 3.4 硅基流动 API

**硅基流动（SiliconFlow）** 是一个模型推理平台，提供按量付费的 AI 模型 API。

| 在项目中的作用 |
|---------------|
| **BGE-M3 嵌入模型**（1024 维）：将简历文本转为语义向量，驱动 ChromaDB 相似度搜索 |
| **PaddleOCR-VL**：识别 JD 截图/图片中的文字 |
| **SenseVoice**：语音转文字，面试复盘时可把录音转成文本 |

**技术选型理由**：相比本地部署嵌入模型（需要 GPU 和 ~4GB 存储），API 模式按量付费（0.14 元/百万 token 输入），个人使用成本极低。项目也支持 `EMBEDDING_MODE=local` 切换本地模式。

## 四、RAG 检索引擎

> RAG（Retrieval-Augmented Generation，检索增强生成）是本项目的核心技术。简单说就是：不是直接把简历和 JD 扔给 AI，而是先"搜索"出简历中最相关的段落，再让 AI 基于这些段落进行重组。这样 AI 不会遗漏关键信息，也不会编造不存在的内容。

### 4.1 向量数据库 — ChromaDB

**ChromaDB** 是一个开源的向量数据库，专为 AI 应用设计。它将文本转换成"向量"（一串数字），语义相近的文本向量距离也近。

| 在项目中的作用 |
|---------------|
| 每份上传的简历切分后存入独立的 ChromaDB Collection（`resume_{id}`） |
| 技能库单独一个 Collection（`skill_library`），跨简历复用 |
| 持久化存储在 `data/chroma/`，重启不丢失 |
| 支持余弦相似度检索，快速找到"意思相近"的内容 |

### 4.2 嵌入模型 — BGE-M3

**BGE-M3** 是 BAAI（北京智源）开发的中文嵌入模型。它能将一段文字（最长 8192 字符）压缩为一个 1024 维的数学向量，语义越相近的文本，向量之间的夹角越小。

| 在项目中的作用 |
|---------------|
| 将简历的每个分块（~400-800 字）转为 1024 维向量 |
| 检索时，将 JD 需求也转为向量，在 ChromaDB 中找最相似的分块 |
| 中文优化：对工作经历、项目描述、专业技能有良好的语义理解 |

### 4.3 BM25 + jieba

**BM25** 是一种经典的关键词匹配算法，和搜索引擎的原理类似。它弥补了向量检索的一个短板：向量检索是"语义相似"，可能漏掉精确关键词。

| 在项目中的作用 |
|---------------|
| **jieba 分词**：对中文文本进行分词（如"熟练掌握Python" → ["熟练", "掌握", "Python"]） |
| **BM25 检索**：找到包含 JD 关键术语（如 "Kubernetes"、"用户增长"）的简历分块 |
| **RRF 融合**：将 Dense（语义）和 Sparse（关键词）的检索结果按排名融合，k=60 |

### 4.4 混合检索流水线

```
JD 需求
  ├─→ BGE-M3 语义检索 (Dense, top_k=15) ─┐
  ├─→ BM25 关键词检索 (Sparse, top_k=10) ─┤
                                          ├─→ RRF 融合 → 章节加权 → 跨领域惩罚 → Top 8
                                          │
简历分块 (ChromaDB) ─────────────────────┘
```

| 步骤 | 说明 |
|------|------|
| Dense 检索 | BGE-M3 向量在 ChromaDB 中找语义最相似的分块 |
| Sparse 检索 | BM25 找到精确包含关键词的分块 |
| RRF 融合 | 合并两路排名，取交集和并集 |
| 章节加权 | 工作经历 ×1.5，项目 ×1.3，技能 ×1.2，教育 ×0.7 |
| 跨领域惩罚 | 不相关领域的分块降权（如求职互联网却被机械/嵌入式经历拉偏） |
| 相关性阈值 | 低于最高分 15% 的结果丢弃，确保质量 |

### 4.5 3 层智能分块器

| 层级 | 粒度 | 说明 |
|------|------|------|
| **L1 章节级** | 整章 | "工作经历"、"项目经历" 等作为完整上下文保留 |
| **L2 条目级** | 单条经历 | 一段工作经历或一个项目，≤800 字符不拆分 |
| **L3 职责级** | 单条职责 | L2 超过 800 字符时按职责点拆分，parent_id 回溯关联 |

| 在项目中的作用 |

```
1. 上传简历 → 解析 → 智能分块 → 向量化 → 存入 ChromaDB

                                          ↓

                                          ↓
```
